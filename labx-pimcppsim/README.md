# CPU–CIM simulator

Run a CPU instruction trace against one computing-in-memory (CIM) macro and one DMA engine. The simulator reports both the matrix–vector result and the cycle at which the CPU can read it. Use the same trace in two modes to measure how much independent CPU work overlaps with the accelerator.

## Build and run

From this directory, use GNU Make and a C++17 compiler (GCC or Clang) to run all three examples.

```sh
make run
```

`make run` builds both executables, runs the standalone CIM demo and both CPU trace modes, prints their reports, and saves them under `results/`. Use `make` to build the executables alone and `make clean` to remove them. The implementation walkthrough follows the same examples. [tutorial.md](./tutorial.md)

| Directory | Contents |
|---|---|
| `simulators/` | [Standalone CIM model](./simulators/cim.cpp), [CPU–CIM simulator](./simulators/cosim.cpp), and [shared timing formulas](./simulators/timing.hpp) |

## Read the CPU trace results

| Mode | Loaded values | DMA output visible at cycle | CPU blocked cycles | Total cycles |
|---|---|---:|---:|---:|
| Default | `7 -10` | 18 | 8 | 19 |
| `--blocking` | `7 -10` | 18 | 14 | 25 |

The six-cycle difference comes from `WORK 6`. In the default mode the CPU does that work while the accelerator is busy. The DMA finishes at the same cycle in both runs. `cpu_finished` marks the end of the CPU trace. `total_cycles` also includes any pending DMA writeback.

## Run your own trace

Copy the example, edit `my.trace`, and run either mode. Use one instruction per line, decimal byte addresses, and `#` for comments.

```sh
cp examples/example.trace my.trace
./build/cosim my.trace
./build/cosim my.trace --blocking
```

To read from standard input and save a custom report, run `./build/cosim - < my.trace > results/my-run.txt`.

| Instruction | Meaning |
|---|---|
| `STORE addr byte...` | Write consecutive bytes starting at `addr`. Accepts signed bytes or raw values up to 255. |
| `PROGRAM addr rows cols` | Load row-major signed 8-bit weights into the macro. The matrix must fit within 64 rows × 32 columns. Weights remain until the next `PROGRAM`. |
| `SUBMIT id input_addr output_addr` | Multiply the input vector by the resident weights. Reserve `rows` bytes for input and `8 × cols` bytes for output. Use a unique job ID for each submission. |
| `WORK cycles` | Spend this many CPU cycles without accessing memory. |
| `WAIT id` | Block until that job's DMA writeback completes. |
| `LOAD addr count` | Read and print `count` signed little-endian 64-bit values. The count is in **values**, not bytes. |

The CPU and DMA share 1 MiB of byte-addressed memory and one 16-byte-per-cycle port. Only one job can be outstanding. Even without `WAIT`, a CPU load from a pending output buffer waits for writeback before reading it.

## Run the standalone CIM model

For arithmetic and accelerator latency, run the standalone model directly.

```sh
./build/cim          # Built-in two-vector demo, expected total_cycles=25
./build/cim --help   # Show the numeric workload format
```

For a custom workload, run `./build/cim workload.txt > results/my-cim.txt`. Supply whitespace-separated integers starting with `rows columns vector_count`, followed by the row-major weights and one input vector of length `rows` per multiplication. Weights and inputs must be in `-128..127`.
